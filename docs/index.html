The contract, both ways.

cancho-client-gen consumes the byte-verified OpenAPI 3.1 document that cancho-web generates and writes strictly typed client libraries, in the pgen tradition: cancho-pg turns queries.sql into typed cancho functions by asking the database; this turns openapi.json into typed clients by reading the document.

One document

The served document is pinned byte for byte by cancho-web's own test. This reads the file, not the running service, and nothing else.

Typed both directions

The server is held to the document by tests; the client is written from the document by this tool. Neither side hand-writes the other's half.

pgen's discipline

pgen asks the database instead of trusting the .sql file; this refuses an invalid document instead of writing half a client.

Why the document, not the declaration.

The declaration is a running program and a second source of truth: a generator that read it would have to run the service or re-read .cho source (cancho-web's design §9.9 says why the same argument rejected generated records there). The document is a file, already verified -- and consuming it keeps the tool useful for any OpenAPI 3.1 producer, not just cancho-web.

Strict types, no coercion

A response body that breaks the schema is refused, not coerced. Every error the document declares as problem+json (RFC 9457) is a typed error the client can switch on.

A class per component

A named shape in the document (User, Page, Problem) is a named class in the client, not an anonymous one. That is why this is sequenced after cancho-web#16: components below the schema root written as $ref, not inline.

The pgen gate

Nothing is written for an invalid document: a file that does not validate as OpenAPI 3.1 produces no output and an error. Committed output, CI regenerates and diffs -- a change to the API is a change to a generated client that review sees.

No foreign call

The clients are cancho over http.client, and cancho authority on the generator itself reports what it can touch. A tool for cancho, built the way cancho's own tools are.

Slices.

The work is sequenced in the epic (#2) and its seven task issues: a JSON reader over cancho's own buffers that refuses an invalid document (#3, built); the model of paths, operations, parameters, bodies, responses and $ref-resolved components (#4, built); the TypeScript target (#5, built); the committed-output gate (#6, built); the Go target (#7, built); the Python target (#8, built); and the first consumer that is cancho itself, a cancho client over http.client (#9, built).

Slices 1 to 6 built: the reader, the model, three targets, the gate
